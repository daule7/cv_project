# Владение мячом по видео матча (Barcelona — Athletic Club)

Для каждого кадра `video.mp4` пайплайн ставит метку H (хозяева), A (гости), D (мяч вне игры) или X (вне игровых отрезков) и считает проценты владения. Также рендерится видео с визуализацией.

## Запуск

```bash
/usr/bin/python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python run.py                          # весь матч: все шаги (demo — отдельным флагом)
.venv/bin/python run.py --demo default           # только demo (первые 2.5 мин 1-го тайма)
.venv/bin/python run.py --demo 120000:123000     # demo любого диапазона кадров
.venv/bin/python run.py --start 11185 --end 26184 --stage detect   # только детекция диапазона
.venv/bin/python run.py --stage teams,ball,possession,report,eval  # пересчёт без детектора
.venv/bin/python run.py --stride 2               # детектор на каждом 2-м кадре (1..5)
```

Аргументы: `--start/--end` — диапазон кадров (0-based, включительно; детектор работает только внутри
игровых отрезков 11185–90651 и 110808–190197); `--stride` — шаг детектора; `--stage` — список шагов
или `all`; `--demo START:END|default`; `--method hmm|baseline` — какой метод пишется в
`out/possession.csv`. Детекция кэшируется чанками по 1000 кадров в `out/detections/` и
**возобновляется** с места остановки (готовые чанки пропускаются).

Устройство выбирается автоматически: cuda → mps → cpu. Проверено на Apple M5 Pro (mps).

## Шаги (src/)

| модуль | что делает | результат |
|---|---|---|
| `detect.py` (шаг 1) | YOLOv8 (`football_yolov8.pt`) на полном кадре imgsz=1920, fp16; ByteTrack (ultralytics) по людям; для мяча до 5 кандидатов на кадр; цвет торса в Lab; маска газона и ближняя бровка (`pitch.py`) | `out/detections/chunk_*.parquet`, `frames_*.parquet` |
| `teams.py` (шаг 2) | голосование класса по треку (судья/вратарь); KMeans(k=2) по Lab торса (верх рамки без зелёных пикселей); голосование команды в скользящем окне ±0.5 с внутри трека; тёмный кластер = H; вратари — по стороне ворот | `out/persons.parquet`, `out/teams.json` |
| `ball.py` (шаг 3) | отбрасывание кандидатов вне газона и ниже ближней бровки; Витерби по кандидатам (скачок > 80 px/кадр запрещён, новый трек только с conf ≥ 0.3); пропуски ≤ 0.5 с — линейная интерполяция | `out/ball.parquet` |
| `possession.py` (шаг 4) | признаки (расстояние мяч→ближайший игрок H/A в высотах рамки, скорость мяча и игроков с поправкой на движение камеры, время без мяча); (а) baseline: ближайший игрок + большинство в окне ±50 кадров; (б) HMM H/A/D + Витерби по таймам | `out/features.parquet`, `out/possession_{baseline,hmm}.csv` |
| `report.py` (шаг 5) | `out/possession.csv` (HMM), проценты по таймам и за матч, число и средняя длина владений | `out/summary.txt` |
| `demo.py` (шаг 5) | рамки цветом команды (H синий, A красный, судьи жёлтый), id трека, кружок на мяче (жёлтый — детекция, оранжевый — интерполяция), плашка «владеет», лента-таймлайн и текущие проценты | `out/demo.mp4` |
| `evaluate.py` (шаг 6) | официальный скорер `possession_metrics.py` (metrica-sports/more-than-a-hack-2027, лежит в `src/vendor/`): accuracy, macro-F1, матрица ошибок, spellF1 | `out/eval.md` |

Формат `out/possession.csv` совпадает с `correct.csv`: `frame,label`, кадры 0…199318, метки H/A/D/X,
X — вне игровых отрезков (так же, как в correct.csv).

## Выбор конфигурации детектора (замеры)

Выборка из 300 случайных игровых кадров, доля кадров с мячом (fp16, mps):

| вариант | к/с | мяч conf≥0.1 | мяч conf≥0.25 | мяч conf≥0.5 |
|---|---|---|---|---|
| полный кадр, imgsz=1280 | 58 | 0.853 | 0.617 | 0.147 |
| полный кадр, imgsz=1920 | 53 | 0.903 | 0.617 | 0.153 |
| тайлы 2×2, imgsz=1280 + NMS | 19 | 0.890 | 0.613 | 0.197 |
| тайлы 3×2, imgsz=1280 + NMS | 14 | 0.917 | 0.707 | 0.330 |

Выбран полный кадр с imgsz=1920. При conf≥0.25 он находит мяч так же часто, как тайлы 2×2, и работает в 3 раза быстрее. Тайлы 3×2 дают +9 п.п., но весь матч на них занял бы ≈3.2 ч на кадр без трекинга, то есть больше бюджета. При stride 2 терялось бы временное разрешение для ByteTrack.
С трекингом, цветом и маской поля скорость 37–39 к/с, весь матч ≈ 70 мин, поэтому **stride = 1**
(интерполяция пропущенных кадров не нужна).

## Константы (заданы заранее, `src/config.py`)

- Мяч: макс. шаг 80 px/кадр (удар ~35 м/с; игрок ~1.8 м ≈ 45 px → ≈ 0.8 высоты/кадр ≈ 35–60 px,
  плюс запас на камеру); интерполяция ≤ 0.5 с; кандидаты conf ≥ 0.1, старт трека conf ≥ 0.3.
- Контроль: ядро exp(−d²/2σ²), d — расстояние до точки ног в высотах рамки, σ = 1 высота (~1.8 м);
  ослабление для быстрого мяча 1/(1+v/0.15 высоты/кадр); сила α = 4.
- HMM: среднее владение 12 с, остановка 25 с; 60 % концов владения — переход к сопернику, 40 % — в D.
  Если мяча нет, свидетельство о команде нулевое: эмиссии H и A равны, состояние удерживается.
- Признаки D: мяч неподвижен (< 0.02 высоты/кадр) и никого ближе 3 высот (+1.0); мяч не виден > 3 с
  (до +1.0 при 6 с); уверенный мяч вне поля, когда в поле мяч не виден > 1 с (+2.0); замедление
  игроков: медианная скорость (с вычетом медианного смещения всех треков = движение камеры) ниже 75 %
  медианы тайма (+1.0 к D), выше 115 % (+0.5 к H и A).
- Темперирование эмиссий: одно независимое наблюдение на 0.2 с, то есть логарифмы правдоподобий × 0.2 при 25 к/с.

### Что поменялось после первой проверки (честно)

Первая версия (v1) прогнана на проверочном фрагменте. После неё сделаны 4 изменения. Ни одно не подбиралось по correct.csv; каждое обосновано диагностикой без меток или визуальной проверкой:

1. Судьи/лайнсмены, которых детектор местами называет `player`, получали цвет команды (видно на
   demo). Добавлено голосование класса по треку.
2. ByteTrack иногда передаёт id игроку другой команды, и голосование по всему треку красило его неверно (видно на demo). Теперь голосование идёт в окне ±0.5 с.
3. HMM v1 давала владения в среднем 5 с при собственном априоре 12 с, потому что эмиссии считались независимыми
   на каждом из 25 кадров в секунду. Введено темперирование (0.2 с на наблюдение).
4. Абсолютные пороги скорости игроков (0.5/1.0 высоты/с) оказались не откалиброваны: медиана по матчу
   0.59, p90 0.90, то есть «быстро» почти не достигалось. Пороги переведены в доли медианы тайма.

Результаты на проверочном фрагменте (30 000 кадров: 11185–26184 и 110808–125807):

| версия | метод | accuracy | macro-F1 | spellF1 |
|---|---|---|---|---|
| v1 | baseline | 0.609 | 0.583 | 0.170 |
| v1 | HMM | 0.594 | 0.584 | 0.120 |
| v2 | baseline | 0.670 | 0.629 | 0.282 |
| v2 | HMM | 0.729 | 0.705 | 0.365 |

Детали: `out/eval_v1.md`, `out/eval_v2_validation.md`. Итог по всему матчу — в `out/eval.md` и
`out/summary.txt`.

## Ограничения

- Мяч: детектор (recall 0.375 по его же метрикам) находит мяч не везде. В воздухе, у ног в толпе и в тени
  он часто теряется. Ложные срабатывания: головы, гетры, разметка; бровка отсекает только ближнюю сторону и не находится,
  когда линия не видна или идёт круто (угловые ракурсы).
- Гомографии нет: расстояния нормируются на высоту рамки. Мяч в воздухе проецируется «рядом» с
  игроками, над которыми летит.
- Команды: часть судей всё ещё окрашена в цвет команды (если детектор почти всегда зовёт их
  `player`); запасные в манишках у бровки попадают в кластеры.
- HMM «липкая»: короткие владения (< 2–3 с, отскоки, единичные касания) сливаются с соседними,
  а быстрый розыгрыш после остановки иногда не распознаётся как D.
- Темперирование и относительные пороги скорости добавлены после первого прогона (см. выше). Их
  значения взяты из рассуждений, но решение их ввести принято после того, как я увидел метрики v1.
